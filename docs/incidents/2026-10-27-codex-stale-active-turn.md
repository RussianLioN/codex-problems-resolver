# Ложный активный шаг после завершения разговора Codex

Дата: 27 октября 2026 года.

Задача: [#14](https://github.com/RussianLioN/codex-problems-resolver/issues/14).
Запрос на слияние: [#15](https://github.com/RussianLioN/codex-problems-resolver/pull/15).

Статус: клиент восстановлен, переключение `/plan` проверено в исходной вкладке;
владелец подтвердил исчезновение `Working` и включение/выключение режима
планирования. Точный первоначальный переход остаётся неизвестным.

## Симптом и окружение

Codex CLI 0.164.0, macOS, iTerm2 3.7.2, общий локальный сервер Codex.
Вкладка показывает `Working`, команда `/plan` отвечает
`'/plan' is disabled while a task is in progress`.
В том же клиенте обзор задач показывает `Ready`, сервер — `idle`.
Последний ответ уже выведен вместе с длительностью выполненной работы.

Проект ai-memory-infra использован только как место наблюдения. Поломка его
службы памяти или продолжающаяся полезная работа этим индикатором не доказаны.

## Воспроизведение и доказательства

1. В затронутом сохранённом разговоре дождаться итогового ответа.
2. Сопоставить `Ready` обзора и `idle` сервера с `Working` вкладки.
3. Ввести `/plan` и увидеть отказ из-за якобы продолжающегося шага.

Это описание наблюдавшегося состояния; начальная последовательность,
вызывающая дефект в чистом сеансе, не установлена.

| Проверка | Наблюдение |
| --- | --- |
| Последний ход | `task_complete` в 12:16:16.177 UTC / 15:16:16.177 МСК |
| Серверный разговор | `idle`; последний ход `completed`, без ошибки |
| История ходов | Нет `task_started` без `task_complete` либо `turn_aborted` |
| Последние инструменты | 28 результатов; нет маркеров продолжающегося выполнения |
| Решение продолжать работу | `needs_follow_up=false`, `has_pending_input=false` |
| Терминальный клиент | Получил итоговый текст; это отдельно не доказывает обработку события завершения |
| Интерфейс | Снимки пользователя показывают одновременно завершённый ответ, запрет `/plan` и `Ready` обзора |

Сопоставлялись идентификатор одного разговора, его каталог, процесс клиента
и терминальная вкладка. Частные идентификаторы, абсолютные пути, содержимое
переписки и сырые журналы в репозиторий не включены.

## Разбор причины

Подтверждённая причина пользовательской блокировки: локальное представление
занятости терминального клиента расходится с состоянием разговора на сервере.
Первоначальное событие, оставившее локальную занятость, не установлено.

В исходниках точной установленной версии найден подходящий механизм:

- После завершения хода локальная занятость пересчитывается как
  `agent_turn_running || review.is_review_mode || mcp_startup_status.is_some()`.
  Ожидание запуска MCP способно сохранить занятость; при одном лишь таком
  ожидании строка выполнения скрывается.
- Обработчик команды учитывает исключение для запуска MCP без пользовательского
  хода. Поле ввода проверяет команду раньше по общему `is_task_running`;
  передача проверки обработчику предусмотрена для `/review`, но не для `/plan`.
- Обзор задач принимает серверный `ThreadStatusChanged`, а виджет разговора
  не использует это уведомление для пересчёта своей локальной занятости.

Источники версии `rust-v0.164.0`:

- [Пересчёт занятости](https://github.com/openai/codex/blob/rust-v0.164.0/codex-rs/tui/src/chatwidget/turn_runtime.rs#L30-L46)
  и [завершение хода](https://github.com/openai/codex/blob/rust-v0.164.0/codex-rs/tui/src/chatwidget/turn_runtime.rs#L182-L198).
- [Ранняя проверка ввода](https://github.com/openai/codex/blob/rust-v0.164.0/codex-rs/tui/src/bottom_pane/chat_composer.rs#L3400-L3414),
  [исключение для Review](https://github.com/openai/codex/blob/rust-v0.164.0/codex-rs/tui/src/slash_command.rs#L221-L225)
  и [последующий обработчик](https://github.com/openai/codex/blob/rust-v0.164.0/codex-rs/tui/src/chatwidget/slash_dispatch.rs#L137-L155).
- [Обновление обзора](https://github.com/openai/codex/blob/rust-v0.164.0/codex-rs/tui/src/app/app_server_events.rs#L285-L296)
  и [обработка событий виджетом](https://github.com/openai/codex/blob/rust-v0.164.0/codex-rs/tui/src/chatwidget/protocol.rs#L362-L391).

Наличие остаточного `mcp_startup_status` в памяти конкретного процесса
не подтверждено. Это условное объяснение из исходников, а не установленный
первоначальный механизм данного случая. Прежний `Transport closed` и ошибки
создания краткого пересказа не считаются доказательством причинной связи.

Stack Overflow for Agents доступен; поиск выполнен, подходящего независимого
свидетельства именно этого случая не найдено. Разбор основан на собственных
наблюдениях и первичных исходниках Codex.

## Восстановление

Перед действием повторно проверить `idle`, отсутствие незавершённых команд
и сохранить несданный текст, если он есть. Штатно выйти командой `/exit`
только из точно сопоставленного клиента. Возобновить прежний разговор:

```sh
codex resume <SESSION_ID> -C <PROJECT_DIR>
```

Идентификатор брать из проверенного разговора; не подставлять `--last`, если
между проверкой и запуском мог появиться другой разговор. Новый запрос модели
для восстановления не нужен. Общий сервер, службы памяти и файлы истории
не перезапускать и не удалять.

Синтаксис подтверждён локальным `codex resume --help` и
[документацией](https://learn.chatgpt.com/docs/cli/reference#codex-resume).
Если одно адресное возобновление не устраняет симптом, прекратить повторные
перезапуски и исследовать оставшееся состояние запуска MCP.

## Фактический результат и проверки

27 октября 2026 года выполнено одно адресное восстановление:

1. Повторно подтверждены `idle` разговора, неизменный последний завершённый ход,
   точное соответствие вкладки и процесса клиента, пустое поле ввода.
2. В 12:39:19 UTC / 15:39:19 МСК команда `/exit` штатно завершила старый клиент.
   Перед запуском нового клиента отдельно проверено возвращение в оболочку.
3. В той же вкладке выполнено `codex resume <SESSION_ID> -C <PROJECT_DIR>`.
   Открылся прежний итоговый ответ с прежним временем завершения 15:16.
4. В 12:40 UTC / 15:40 МСК команда `/plan` реально выполнена через интерфейс
   iTerm2. Клиент показал переход в `Plan mode`; ошибки запрета больше нет.
   Проверка относится к обработке команды и экрану, а не к физическим клавишам.
5. Серверный процесс сохранился; в истории не появился новый запрос модели.
   Повторное чтение разговора вернуло `idle` и тот же последний завершённый ход.
6. Название вкладки, `terminalIconName` и `terminalWindowName` больше не содержат
   индикатора работы. Владелец отдельно подтвердил исчезновение `Working`
   на самой вкладке iTerm2, затем включение и выключение режима планирования.
   Исходный пользовательский сценарий восстановлен.

При программной проверке сеанс переведён в режим планирования, который
пользователь пытался включить; затем владелец проверил оба направления.
Службы памяти, общий сервер, настройки iTerm2 и файлы истории не изменялись.
Команды отправлялись только выбранному сеансу, с отключённой рассылкой ввода.

Выполнены `git diff --cached --check`, `python3 scripts/validate_repository.py`
и `python3 scripts/repository_policy.py validate` — все успешно. Проверки
изменённой логики не добавлялись: изменение репозитория содержит документацию,
установленный Codex не исправлялся. Полный набор выполняется штатной проверкой
запроса на слияние.

Общий урок сохранён в `projects/lessons`, сведения инцидента —
в `projects/codex-problems-resolver`. Обе записи независимо прочитаны через MCP
и сравнены с подготовленным текстом: совпадение после удаления краевых
пробелов и переводов строк. В них сохранена та же граница доказанности.
Отдельная рецензия двух изменённых файлов существенных замечаний не выявила.

## Риски и откат

Восстановление клиента не устраняет дефект исходников Codex и не доказывает
его точный первоначальный механизм. При повторении нужен новый снимок
состояний до вмешательства. Нельзя объявлять происшествие вызванным MCP
только по надписи `Working` или наличию процессов `node_repl`.

Изменение содержит только документацию. Откат документа выполняется отдельным
revert-коммитом по правилам GitOps. Повторное возобновление сохранённого
разговора остаётся способом вернуться к работе без удаления истории.

## Урок

Статус клиента, состояние разговора, состояние дочерней команды и полезный
результат — разные наблюдения. Сначала сопоставить их для одного разговора,
затем восстановить только установленный неисправный компонент. Ответ
инструмента сам по себе не гарантирует завершение дочернего процесса.
Предполагаемый механизм отделять от доказанной причины, а результат
восстановления фиксировать только после проверки исходного сценария.
