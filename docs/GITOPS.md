# GitOps для инцидентов Codex

## Источник истины

Git является источником истины для описания инцидентов, доказательств, планов исправления, проверок, запросов на слияние, откатов и итоговой сверки. Задачи GitHub фиксируют проблему и обсуждение, а файлы репозитория фиксируют устойчивые артефакты: разборы, инструкции, проверки и правила.

Этот репозиторий не является фиктивной системой выкладки. Пока нет конкретной управляемой целевой среды, здесь не должно быть утверждений про действующий механизм применения во внешнюю систему.

## Жизненный цикл инцидента

1. Создать задачу GitHub через шаблон инцидента.
2. Описать симптом, окружение, воспроизведение, доказательства, ожидаемое поведение, риск и подтверждение редакции секретов.
3. Если доказательства длинные или должны жить дольше обсуждения, создать файл `docs/incidents/YYYY-MM-DD-<slug>.md`.
4. Создать ветку `fix/<issue>-<slug>` от актуальной основной ветки.
5. Сформулировать план отдельно от применения: что меняется, почему, как проверить, как откатить.
6. Внести минимальное исправление, тест или документационное правило.
7. Запустить доступные проверки и записать точные команды с результатами.
8. Открыть запрос на слияние по шаблону.
9. После просмотра выполнить squash merge.
10. После слияния сверить основную ветку с ожидаемым состоянием и закрыть задачу только после подтверждения.

## Пути инцидентов и инструкций

Разборы инцидентов размещаются по шаблону:

```text
docs/incidents/YYYY-MM-DD-<slug>.md
```

Файл инцидента должен содержать дату, краткий симптом, окружение, шаги воспроизведения, доказательства, первопричину, исправление, проверки, риски и ссылки на задачу и запрос на слияние.

Повторяемые инструкции размещаются в:

```text
docs/runbooks/
```

Инструкция должна быть пригодна для повторного выполнения: предусловия, команды, ожидаемый результат, признаки ошибки, действия восстановления и правила редакции чувствительных данных.

## Разделение плана и применения

План описывает предполагаемые действия, риск, проверки и откат. Применение меняет файлы. Нельзя выдавать план за выполненную работу и нельзя считать изменение завершённым без фактических проверок или явного объяснения, почему проверка недоступна.

Команды управления репозиторием должны быть воспроизводимыми и строиться на Python 3 со стандартной библиотекой. До появления таких команд в `scripts/` их нужно описывать как планируемые, а не как существующие.

Сверка политики GitHub имеет два режима. `full` является режимом по умолчанию и требует отдельный fine-grained token или GitHub App только для этого репозитория с Repository Administration read, чтобы читать Actions permissions и полный ruleset detail. `builtin` работает с `github.token`, не обращается к admin-only endpoints и сообщает `NOTICE` о непроверенных частях. Не используйте широкий пользовательский OAuth-токен для плановой сверки.

## Секреты и доказательства

В репозиторий нельзя добавлять секреты, токены, пароли, cookie, одноразовые коды, приватные ключи, полные заголовки авторизации и необезличенные журналы с персональными данными. Перед добавлением доказательств заменяйте чувствительные значения стабильными маркерами:

```text
<REDACTED_TOKEN>
<REDACTED_COOKIE>
<USER_HOME>
<PRIVATE_HOST>
```

Если есть сомнение, что значение является секретом, считайте его секретом до проверки владельцем.

## Откат

Откат выполняется через отдельный запрос на слияние. Предпочтительный способ — revert-коммит исходного изменения. Если нужен ручной откат, запрос на слияние должен объяснить, почему обычный revert не подходит, какие файлы меняются и какие проверки подтверждают восстановление.

После отката нужно обновить связанную задачу: что отменено, какие проверки прошли, какие риски остались и требуется ли новый план исправления.

## Исключение начальной настройки

Ветка `chore/gitops-bootstrap` является исключением начальной настройки. В ней допустимо добавить правила, шаблоны и документацию до появления полной автоматизации. Это исключение не разрешает добавлять секреты, несуществующие целевые среды, ручную имитацию выкладки или непроверяемые заявления.

После завершения начальной настройки новые инциденты должны идти через обычный поток: задача, доказательства, ветка `fix/<issue>-<slug>`, проверка, запрос на слияние, squash merge и сверка после слияния.

## Аварийный доступ

Аварийное действие допустимо только при немедленном риске потери доступа, данных или управляемости. Такое действие нужно записать в задаче или файле инцидента:

- причина аварийного действия;
- кто и когда выполнил действие;
- какие команды или ручные шаги были выполнены;
- какое состояние получилось;
- какие проверки прошли после восстановления;
- как состояние возвращено под управление Git.

Аварийное действие не закрывает инцидент само по себе. После него нужен обычный запрос на слияние, который фиксирует восстановление правил, документации или проверок.

## Будущая сверка с целевой средой

Сверка с внешней средой возможна только после появления конкретного управляемого объекта: службы, конфигурации, набора файлов или иной цели с проверяемым состоянием. До этого будущие команды сверки можно проектировать, но нельзя описывать как действующий механизм применения.
